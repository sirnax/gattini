# Task 13 — Codex worker transport discovery

Read-only discovery recorded 2026-09-26. No provider request, login check, model-catalog request, runtime configuration change, install, service start, or worker implementation was performed. This note prepares Task 13; it does not satisfy its live verification acceptance.

## Scope and decision

Task 13 requires a version-matched Codex worker adapter that uses the user's normal configured authentication, reports capabilities honestly, and refuses requirements it cannot safely enforce. Its live acceptance still requires an approved read-only task and comparison of the actual runtime model and session identity with persisted records.

The installed CLI exposes two plausible transports:

1. **`codex app-server` over stdio** is the strongest candidate for a complete worker lifecycle. The current CLI describes the command as experimental, but its help exposes stdio and Unix/WebSocket transports. The official App Server protocol documents explicit thread and turn IDs, event streaming, exact-thread continuation, `turn/interrupt`, and approval request/response flows. This path could represent continuation, cancellation, and approval state directly. However, it requires protocol negotiation, and methods/fields may be marked experimental or beta. Pin the app-server protocol generated by the installed CLI and reject unsupported requirements. Do not treat the published current protocol as proof that installed 0.157.1 supports every documented method.

2. **`codex exec --json` as a child process** is the simpler baseline and is explicitly documented for non-interactive automation. Installed help provides `--json`, `--model`, `--sandbox`, `--ask-for-approval`, `--cd`, `--ephemeral`, `--output-schema`, and exact-ID `codex exec resume`. It can use the user's saved CLI authentication. `thread.started` supplies an explicit ID; JSONL events provide progress/result parsing. The CLI help exposes no explicit cancel subcommand for `exec`; terminating an owned process is not yet proven to cancel the underlying turn. Resume exists, but must be tested to ensure the saved session retains the pinned sandbox and approval configuration. Treat cancellation and resume policy as unsupported until a controlled live check proves them.

**Recommendation:** prototype against app-server stdio first if its experimental status is acceptable for a version-pinned adapter; otherwise implement only the explicitly supported `exec` slice and mark cancellation/follow-up unavailable until proved. Do not advertise the Codex adapter as satisfying the full worker contract from help output alone. No adapter has been selected by an ADR.

## Installed version and read-only commands

`command -v codex` resolved `/opt/homebrew/bin/codex`; `codex --version` returned **`codex-cli 0.157.1`**. This supersedes the earlier Task 1 inventory in `docs/compatibility.md`, which recorded `0.156.1`. The binary printed a sandbox warning that it could not create PATH aliases (`Operation not permitted`); the requested version/help output was still returned.

Commands run, all help/version inspection only:

```text
command -v codex
codex --version
codex --help
codex exec --help
codex exec resume --help
codex app-server --help
codex app-server generate-ts --help
codex agents --help
codex queue --help
codex mcp --help
codex debug --help
```

The installed `codex exec --help` includes these relevant flags:

- `--model <MODEL>` and `--profile <CONFIG_PROFILE_V2>`
- `--sandbox read-only|workspace-write|danger-full-access`
- `--ask-for-approval on-request|never`
- `--cd <DIR>`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`
- `--json` for JSONL events, `--output-schema <FILE>`, `--output-last-message <FILE>`
- `--config <key=value>` for CLI configuration overrides

The installed resume help accepts an exact session UUID/name and another prompt, plus model, profile and config overrides and `--json`; it does not list the `--sandbox` or `--ask-for-approval` shorthand. Verify effective policy on resumed sessions before claiming safe continuation.

`codex app-server --help` reports `[experimental]`, defaults to `stdio://`, and lists stdio, Unix socket, WebSocket and disabled transports. `codex app-server generate-ts --help` can generate bindings and has an `--experimental` switch. `codex agents` and `codex queue` operate on saved/shared app-server sessions, but help does not provide a direct cancel operation for a `codex exec` child.

## Capability map from help and official docs

| Gattini capability | Discovery evidence | Current status |
| --- | --- | --- |
| Headless execution | `codex exec`; official non-interactive mode documents pipeline use | Candidate supported; no execution attempted |
| Explicit session identity | `thread.started` JSONL event documented; app-server returns thread ID | Candidate supported; live identity/model resolution unverified |
| Event stream | `codex exec --json` JSONL events; app-server thread/turn/item notifications | Candidate supported; installed event payloads not captured |
| Read-only policy | `codex exec` defaults to read-only per official docs; installed `--sandbox read-only` flag exists | Candidate enforceable sandbox, but not verified on this host or live task |
| Follow-up | `codex exec resume <SESSION_ID> [PROMPT]`; app-server `thread/resume` + `turn/start` | CLI continuation candidate; session policy inheritance must be verified |
| Cancellation | Official app-server protocol exposes `turn/interrupt`; `exec` help has no cancel command | App-server candidate; `exec` process-signal semantics unverified |
| Approval routing | `exec` exposes approval policy; app-server docs describe request/decision messages | `exec`'s Gattini-level approval handoff is unverified; app-server can represent decisions, but live support/version compatibility is unverified |
| Structured output | `--output-schema`, `--output-last-message`, and JSONL event stream | Candidate; schema failure/event mapping needs fixtures |
| Runtime/model identity | `--model` requests a model; current app-server docs return provider metadata | Requested identity can be pinned; actual resolved model/session identity remains unverified |
| Usage reporting | JSONL completion sample includes token counts in current docs | Availability and completeness on installed version unverified; cost not established |
| Execution containment | Read-only sandbox candidate; workspace write and full access modes also exposed | Read-only mode may support review tasks, but it is not a Gattini-owned isolated worktree or verified host boundary; do not claim general containment |

The official docs describe `codex exec --json` as a JSONL stream with `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*`, and `error` events. The App Server guide documents `thread/start`, `thread/resume`, turn events, `turn/interrupt`, and server-initiated approval requests. Those are current official references and may be newer than installed 0.157.1; installed help is the evidence for flags available locally, while protocol behavior still requires version-matched verification.

## Offline fixtures to prepare during implementation

No fixtures were created in this discovery-only assignment. Task 13 implementation should add sanitized JSONL/protocol fixtures and fake-process tests covering:

- successful run: thread start, turn start, assistant output, turn completion and usage;
- explicit failed turn, process nonzero exit, malformed/truncated JSONL, unknown event type and missing terminal event;
- duplicate, missing, malformed or conflicting session/thread IDs;
- command/tool item start-complete pairs and bounded event count/size/redaction;
- `exec` continuation by exact ID, wrong ID, and resume with effective sandbox/approval mismatch (must reject);
- app-server approval request, decline/cancel response, pending approval at disconnect, late resolution, and request-ID/thread-ID mismatch;
- app-server interruption acknowledged for the exact thread/turn, interruption racing completion, disconnect before interrupt acknowledgement, and process death;
- runtime unavailable, timeout, spawn failure, auth error surfaced without exposing credential text, and model/provider resolution mismatch;
- unsupported requested capabilities rejected before launch; never infer cancellation, approvals, containment, or usage from absent events.

Keep example IDs, prompt contents, paths and usage synthetic or sanitized. Offline fixtures prove parser and state-machine behavior only; they cannot establish Codex runtime support.

## Approval boundary and next evidence

This discovery did not check authentication status or call any provider. A future live probe must wait for the Task 12 dependency/checkpoint path and fresh human approval. The approved probe should be one bounded, read-only task in a disposable repository with an exact configured model and a small explicit spend ceiling if metering permits; capture the resolved model, exact thread/session identity, runtime version, read-only policy, event stream, usage, and final status. If hard spend cannot be guaranteed, say so and wait for explicit approval of the best-effort exposure.

Before running it, confirm the transport and installed version, do not change global Codex config, do not enable services, and do not use write/full-access modes. Validate interruption separately before enabling Gattini cancellation. If the interface cannot provide confirmed cancellation or the required approval route, declare the relevant capability unsupported and refuse jobs that require it. Update `docs/compatibility.md` and the Task 13 roadmap evidence only after approved observed results; record an ADR only after the interface choice is accepted.
