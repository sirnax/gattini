# Task 10 CLI contract (frozen 26 September 2026)

Task 15 local release 0.1.0 adds a read-only `hello` request before every CLI command. Its response is `{version:"0.1.0",protocolVersion:1,databaseSchemaVersion:7}`. Packaged CLI requests carry `clientVersion`; the daemon rejects a different supplied version with `VERSION_MISMATCH` before dispatch. The CLI exits 3 on mismatch and submits no job. An older daemon without `hello` is reported as incompatible. Protocol v1 still accepts requests that omit `clientVersion` for compatibility with existing direct callers; such callers do not receive the CLI's version guard. This release makes no event-cursor or artifact-content RPC claim. Task 17 needs an explicitly versioned addition before editor reconnect/evidence views can be implemented.

`gattini run` accepts the same task, role, idempotency, and trusted-code options as `start`, plus `--poll-ms N` (integer 100–5000; default 500) and `--cancel-on-interrupt`. It submits once through the existing durable `start` method, then polls `status` and retrieves `result` at a terminal state. No daemon protocol change is required. A retry with the same idempotency key observes the same job; it does not create another attempt.

`--json` emits exactly one JSON object on stdout. At a terminal state it is the existing `result` envelope `{jobId,state,result}`. At `awaiting-approval` it is `{jobId,state,approvalId}` when submission supplied an approval ID; subsequent approval waits may omit `approvalId`, so callers use `approvals list` and exact IDs. `run` exits 4 at this state, leaving the job durable. It never auto-approves. Other machine-readable commands retain their existing success response shape. CLI validation and connection errors emit `{error:{code,message}}` on stderr, with stdout empty. Daemon errors use the same stderr shape. Human output goes to stdout on success and stderr on error; untrusted content is escaped for display.

Exit codes: 0 means the CLI command completed and the job's execution is completed without failed acceptance; `acceptance: unverified` remains unverified and must not be claimed as passed. 1 means a terminal job failed, was cancelled or interrupted, or its result has failed execution or acceptance. 2 means invalid CLI input. 3 means daemon, protocol, or other request failure. 4 means an approval is required for further progress. `status` and `start` report successful queries/submissions with exit 0 regardless of job state; `result` and `run` use the terminal outcome rule.

`run` waits indefinitely while the daemon is reachable and the job is active. A transient daemon disconnection exits 3 and prints the exact job ID in the diagnostic; the job remains durable. Ctrl-C exits 130 (SIGTERM exits 143). By default signals do not cancel the job. With `--cancel-on-interrupt`, `run` sends an exact-ID `cancel` request on SIGINT/SIGTERM, then exits with the signal code; if that request fails it reports the failure on stderr. Callers can reconnect with `status JOB_ID` and `result JOB_ID`. No CLI process owns the daemon or runtime lifetime.

Task 13 adds the experimental `codex-reviewer` role after Checkpoint 4. It reads a private `codex-role.json` in Gattini's state directory with exact fields `{ "schemaVersion": 1, "runtime": "codex", "model": "...", "modelProvider": "openai", "directory": "/absolute/path", "executable": "codex" }`. A submitted job is a single read-only Codex app-server turn with no automatic approval grants. Its result remains `acceptance: unverified`; `followup` and coding through this role are unsupported. One separately approved live Task 13 read-only turn returned the requested answer and matching configured identity; cancellation and cross-runtime behavior were not established by it.

Task 14 preserves the command and JSON envelopes while adding private runtime selection. `--role reviewer` reads `roles.json` with `schemaVersion: 1` and a `roles.reviewer` entry for either the existing OpenCode reviewer schema or the Codex schema above without its top-level `schemaVersion`. `--role code --trusted-local-code --require-approval` reads `code-role.json`: either the existing OpenCode code config or `{ "runtime": "codex", "model": "...", "modelProvider": "openai", "executable": "codex" }`. Both code mappings use the same two exact Gattini approvals and validated single-file patch/snapshot result. A read-only runtime may return the strict byte patch or a unique literal `{path,oldText,newText}` edit, which Gattini converts to the historical patch before the apply approval. `codex-reviewer` and its separate file remain available for Task 13 compatibility. Approved Task 14 live review, guarded code apply, and active cancellation have been observed on both runtimes.
